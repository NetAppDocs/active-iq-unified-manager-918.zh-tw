= 回應 Active IQ Unified Manager 中的動態 QoS 限速事件
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
您可以使用 Unified Manager 來調查服務品質（QoS）原則群組限制工作負載處理量（MB/s）所引起的效能事件。此限制增加了原則群組中 Volume 工作負載的回應時間（延遲）。您可以利用事件資訊來確定是否需要對原則群組設定新的限制以停止此限制。

.開始之前
* 您必須擁有操作員、應用程式管理員或儲存管理員角色。
* 必須有新的、已確認的或已過時的效能事件。


.步驟
. 顯示 *事件詳細資料* 頁面以檢視事件的資訊。
. 請閱讀*執行摘要*，其中顯示受節流影響的工作負載名稱。
+
[NOTE]
====
執行摘要可能會顯示受害者和霸凌者相同的工作負載，因為限制使得工作負載本身成為受害者。

====
. 使用文字編輯器等應用程式記錄 Volume 的名稱。
+
您可以搜尋 Volume 名稱，以便稍後找到它。

. 在「工作負載延遲」和「工作負載使用率」圖表中，選取 *惡霸工作負載*。
. 將游標停留在圖表上，即可檢視影響原則群組的前幾大使用者定義工作負載。
+
清單頂部的工作負載偏差最高，並導致發生節流。活動是每個工作負載所使用的原則群組限制百分比。

. 在 *建議操作* 區域中，按一下排名最高之工作負載的 *分析工作負載* 按鈕。
. 在「工作負載分析」頁面中，將「延遲」圖表設定為檢視所有叢集元件，將「處理量」圖表設定為檢視細分情況。
+
細分圖表顯示在延遲圖表和 IOPS 圖表下方。

. 比較 *延遲* 圖表中的 QoS 限制，以了解事件發生時限速程度對延遲的影響。
+
QoS 原則群組的最大處理量為每秒 1,000 次操作（op/sec），其中的工作負載不能共同超過此限制。在事件發生時，原則群組中的工作負載總處理量超過 1,200 op/sec，導致原則群組將其活動限制回 1,000 op/sec。

. 將 *讀取/寫入延遲* 值與 *讀取/寫入/其他* 值進行比較。
+
兩張圖表都顯示讀取請求數量多且延遲高，但寫入請求的數量和延遲都較低。這些數值有助於您判斷是處理量過高還是操作次數過多導致了延遲增加。您可以參考這些數值來決定是否對處理量或操作次數設定原則群組限制。

. 使用 ONTAP System Manager 將原則群組的目前限制增加至 1,300 op/sec。
. 一天後，返回 Unified Manager，並在 *工作負載分析* 頁面中輸入您在步驟 3 中記錄的工作負載。
. 選取「處理量細分」圖表。
+
顯示讀取/寫入/其他圖表。

. 在頁面頂端，將游標指向原則群組限制變更的變更事件圖示（image:../media/opm_change_icon.gif["更改事件圖示"]）。
. 將 *讀取/寫入/其他* 圖表與 *延遲* 圖表進行比較。
+
讀取和寫入請求相同，但限速已停止，延遲已降低。
